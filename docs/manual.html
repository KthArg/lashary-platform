LASHARY Beauty Studio · equipo de 6 · sprints de 2 semanas

Manual de operación del repositorio

Todo lo que necesitás para trabajar en lashary-platform: cómo instalarlo, cómo empezar y cerrar una tarea, qué comandos existen y por qué el repositorio se defiende solo.

01Qué es esto

Una plataforma de gestión de clientas y agendamiento para LASHARY Beauty Studio — un único estudio de belleza (no SaaS, no multi-sede). La administradora gestiona catálogo, agenda, clientas, pagos y morosidad; la clienta reserva, reagenda y ve su cuenta; el público ve la landing y el blog.

StackNext.js (App Router) · Supabase (PostgreSQL, Auth, RLS, Storage) · Tailwind + DaisyUI
ContenidoCMS propio externo, repo aparte, consumido por API (ADR-0001)
DeployVercel · CI en GitHub Actions
Alcance51 historias del backlog de Jira — fijas; no se crean historias nuevas (ADR-0007)

02Instalación

Una vez por máquina. En Windows, usá Git Bash para los scripts (viene con Git).

  1. Requisitos

    Git (con Git Bash en Windows) y Node.js LTS. Opcionales pero recomendados: GitHub CLI (gh) y Claude Code — los comandos /algo de este manual corren dentro de Claude Code.

  2. Clonar

    git clone https://github.com/KthArg/lashary-platform
cd lashary-platform

  3. Instalar los hooks obligatorio

    bash scripts/install-hooks.sh

    Activa el pre-commit que corre las mismas verificaciones que CI, en segundos y antes del push. Sin esto, tus errores los descubre CI diez minutos más tarde.

  4. Comprobar que todo funciona

    bash scripts/verify.sh

    Debe terminar en ✔ verify: 10 checks, todos en verde. Si algo falla en un clon limpio, avisá al equipo — es un problema del repo, no tuyo.

  5. Orientarte

    Leé README.md y después docs/STATUS.md. Ese orden. STATUS.md es siempre lo primero que se lee al retomar trabajo.

03Cómo funciona el repo

Las reglas tienen ID, y el repo las hace cumplir

Cada regla del proyecto vive en docs/spec/rules.yaml con un ID permanente — ARCH-003 DOM-001 EST-002 — su enunciado, su porqué, y su capa de cumplimiento. Cuando CI o el pre-commit te bloquean, el mensaje cita la regla exacta, su racional y el documento donde vive. No es burocracia: es que "rompiste una regla" sea un hecho verificable y no una opinión en un review.

CapaQué es¿Te puede bloquear?
L1 — CIScripts deterministas (scripts/rules/). La única compuerta realSí — build rojo
L2 — localLos mismos scripts en tu pre-commitSí — commit bloqueado
L3 — estructuraLo imposible de romper: exclusion constraint, RLS, tipo Money, ESLintNo compila / la base lo rechaza
L4 — IASkills y agente revisor. Detección temprana, no un controlNo — solo avisa
L5 — humanos2 aprobaciones por PR, checklist del templateSí — sin aprobar no hay merge

El estado vive en el repo, y es generado

Cada feature tiene un SPEC.md cuyo encabezado (front-matter) dice, con vocabulario cerrado, en qué está cada historia: no_iniciada, en_progreso, bloqueada, en_revision o terminada. Nada más — ni porcentajes ni "casi listo". De ahí, scripts/status-gen.sh genera docs/STATUS.md. CI compara el STATUS commiteado contra el regenerado: si difieren, build rojo (EST-002). Mismo principio que un lockfile — un archivo de estado escrito a mano miente; uno derivado no puede.

  • terminada exige la evidencia: el PR que la cerró (EST-005).
  • bloqueada exige el ID que la bloquea (EST-004).
  • en_progreso exige el faltante en una frase concreta: "la prueba de concurrencia no existe", no "falta pulir".

Features verticales, fronteras duras

Cada feature (scheduling, payments, clients…) contiene todo lo suyo: dominio, casos de uso, UI y sus tablas (con su prefijo: scheduling_appointments). Entre features solo se importa el index.ts público (ARCH-003); la capa domain/ no importa de ninguna otra feature (ARCH-004). Así dos personas trabajan features distintas sin pisarse.

El backlog manda, y algunas historias pesan doble

Las 51 historias de Jira son el alcance. Por decisión del PO (ADR-0007) no se crean historias nuevas: la infraestructura (bitácora, ledger de pagos, canal de WhatsApp/email, gateway del CMS…) se construye dentro de la primera historia que la exige. La tabla de "historias portadoras" está en docs/process/DEPENDENCIES.md — consultala al estimar: US-AGE-13, US-AGE-12, US-NOT-03, US-MOR-03 y US-AGE-09 cargan más trabajo del que sugieren sus puntos.

04Empezar una tarea

Con Claude Code (recomendado) o a mano — el bucle es el mismo y corre siempre, lo pidas o no.

  1. Abrí un chat nuevo en la carpeta del repo

    cd lashary-platform
claude

    Las skills del proyecto se cargan solas. Al iniciar, Claude lee STATUS.md, el SPEC de la feature y las reglas — está obligado a declararte qué historia, qué reglas aplican y qué dice el estado antes de tocar nada.

  2. Elegí qué trabajar

    /empezables

    Lista qué historias pueden arrancar ya (todas sus dependencias terminada) y cuáles están bloqueadas y por quién. Una historia con dependencias incompletas no se empieza (INT-007) — se dice y se elige otra.

  3. Abrí el bucle

    /trabajar US-AGE-08

    Orienta, verifica dependencias, te muestra los criterios de aceptación del backlog y las reglas aplicables. Si un criterio no es verificable objetivamente, se señala antes de implementar.

  4. Ramificá y trabajá en incrementos chicos

    git checkout -b feat/age-08-catalog

    Desde main, siempre. La rama vive máximo 3 días (INT-001). Si la tarea es más grande, se parte: lo que funciona se mergea apagado tras un feature flag con dueño y fecha de retiro (INT-004).

Trabajás sin Claude

El bucle manual es el mismo: leé docs/STATUS.md → el SPEC.md de tu feature → los criterios en docs/backlog/ → verificá dependencias en DEPENDENCIES.md → implementá. Está escrito completo en docs/process/WORK_LOOP.md.

05Cerrar una tarea

  1. Verificá — de verdad

    /verificar   # o: bash scripts/verify.sh + las pruebas

    Corre los checks y las pruebas, y mapea cada criterio de aceptación a la prueba que lo demuestra. Criterio sin prueba = no cumplido, sin discusión. La regla de oro del proyecto: nunca se dice "esto debería funcionar" — o se verificó, o está en_progreso con el faltante nombrado.

  2. Actualizá el estado

    /regenerar-estado   # edita el SPEC.md y corre scripts/status-gen.sh

    El front-matter de tu feature refleja lo real: historia a en_revision, deuda tomada con su costo, exactamente dónde se detiene lo incompleto. Después se regenera STATUS.md — jamás editándolo a mano.

  3. Pasá la compuerta

    /listo-pr

    Devuelve PASS o la lista exacta de bloqueos: diff ≤ ~400 líneas y ≤ 2 features con código (INT-002), máximo 1 migración (INT-008), SPEC actualizado, STATUS fresco, fronteras limpias.

  4. Abrí el PR

    git push -u origin feat/age-08-catalog
gh pr create

    El template del PR pide: la salida de verify.sh pegada (no descrita), la tabla criterio → prueba, y el checklist con IDs de regla. Commits y nombres de rama en inglés; el PR se mergea con squash.

  5. Checks + revisión

    CI corre las reglas; el agente pr-compliance comenta hallazgos con sus IDs (es consejo, no compuerta). Necesitás 2 aprobaciones, al menos 1 de alguien que no trabaja en esa feature (INT-005). Rebase sobre main antes del merge. El estilo no se discute en review jamás: si el linter debió atraparlo, el fix es un PR a la config del linter (INT-006).

  6. Merge y cierre

    Squash merge (la rama se borra sola). La historia pasa a terminada con el número de PR como evidencia en el SPEC — y STATUS.md regenerado en ese mismo PR o el siguiente.

¿Necesitás romper una regla?

Hay camino legítimo, y es más barato que el silencioso: una excepción de arquitectura se documenta en un ADR (/nuevo-adr); una de proceso, en un PR etiquetado excepcion-proceso con justificación escrita. Detalle en docs/spec/INTEGRATION.md.

QuéCuándoQué hacePoder

Límites fijos de todos los agentes: jamás aprueban, mergean, pushean a main, corren migraciones fuera de local ni tocan credenciales de producción. Su palabra es consejo; la compuerta son CI y los 2 revisores humanos. Y el código generado por IA se revisa completo, sin descuento de confianza — el autor del PR es dueño de cada línea, la haya tecleado quien sea.

09Problemas frecuentes

El pre-commit me bloqueó el commit

Leé el mensaje: cita la regla, el porqué y el archivo exacto. Arreglá eso y volvé a commitear. Está diseñado para frenarte a vos antes de que CI se lo cuente a todo el equipo — le pasó hasta a la IA que construyó el repo.

CI dice que STATUS.md está desactualizado

bash scripts/status-gen.sh, commiteá el resultado. Pasa cuando editaste un SPEC y olvidaste regenerar.

Mi historia depende de otra que no está terminada

No se construye sobre cimientos ausentes. Decilo en el canal del equipo, elegí otra con /empezables. Si solo un criterio depende de algo futuro, mirá "criterios diferidos" en DEPENDENCIES.md: se implementa tras un flag y la historia queda en_progreso con el faltante nombrado.

El PR se me pasó de 400 líneas

Partí la tarea. Lo que ya funciona se mergea apagado tras un feature flag (con dueño y fecha de retiro en el SPEC). Un flag que venció y sigue vivo lo caza CI.

¿Dónde están los criterios de aceptación de mi historia?

En el CSV de docs/backlog/ — o directo con /historia US-XXX-NN. El backlog de Jira es la fuente; el repo guarda una copia versionada.

Quiero agregar una librería o herramienta

Dependencias normales: PR normal (Dependabot vigila vulnerabilidades). Herramientas con acceso al repo o al entorno (actions, MCP, CLIs): primero /auditar-herramienta, allowlist con hash, versión pinneada. Empezá por docs/tooling-candidates.md — ya hay una lista evaluada con veredictos.
